# CAgent integration architecture

Status: planned, 2026-10-08. CAgent has an independent Server API available only inside the target environment. No CAgent endpoint, schema, feature or successful integration has been verified here.

This urgent requirement precedes the other implementation work in the [integration milestones](OPENCODE-INTEGRATION-MILESTONES.md). It extends [the integration SPEC](OPENCODE-INTEGRATION-SPEC.md) and supersedes its former exclusion of an independent agent server. CAgent is a named second backend family; a general plugin marketplace and arbitrary protocol framework remain outside scope. English is the implementation handoff; the [Chinese copy](zh-CN/CAGENT-INTEGRATION-SPEC.md) follows the shared bilingual review rules.

## Delivery split and ownership

The architecture owner prepares a working adaptation kit before handing work to the environment-local agent. The local agent reads the supplied API documentation and changes only a generated CAgent adapter workspace. It does not redesign shared UI, stores, scheduling, authentication or transport. A maintainer reviews the resulting evidence and authorizes activation in that environment.

| Delivery | Owner and evidence |
| --- | --- |
| Shared contracts and isolation | Architecture owner extracts the actual consumed contracts and migrates SDK leaks with OC1/OC2 regressions. |
| Adaptation kit | Architecture owner delivers compiling stubs, schemas, an example adapter, fixed tests, offline dependencies and short task packets. Deliberately incomplete adapters must fail the relevant checks. |
| Real CAgent implementation | Local agent maps documented operations, supplies sanitized fixtures and implements bounded codecs/transport hooks inside the allowed workspace. |
| Acceptance | Local maintainer verifies the real server, enabled features, disabled features and extension behavior. Simulation alone cannot pass CAgent acceptance. |

The kit is an implementation deliverable of CA-02, not something already generated by these planning documents. Its executable commands and exact file paths are frozen in CA-02 from the actual repository. The [adapter workbook](CAGENT-ADAPTER-WORKBOOK.md) defines the kit's inputs, outputs and local workflow now. Before CA-01 implementation, use the frozen [consumer boundaries](CAGENT-BOUNDARIES.md) and its complete method disposition registry.

## Backend identity and dispatch

Add a backend-family discriminator to the existing authoritative descriptor. OpenCode retains OC1/OC2 generation and its Auto/OC1/OC2/Legacy selection. CAgent has its own adapter ID, adapter revision, contract version, server identity/version provenance and capability revision. OpenCode generation/profile fields are not required or fabricated for CAgent. Backend selection, connection mode and compatibility selection remain distinct.

CAgent selection is explicit. Auto continues to resolve OpenCode profiles only; a failed OpenCode probe never selects CAgent. A CAgent adapter can verify identity only with a documented read-only probe. Missing version information remains user-declared/unverified. Endpoint, auth identity, backend family or adapter replacement retires the connection epoch. Capability changes invalidate affected availability decisions and are rechecked at dispatch. Preserve queued intent under its original identity; do not replay it on another backend.

Initially support CAgent as an explicitly configured external server. Managed server-command launch is added only when its start/readiness/shutdown contract is documented and tested. PATH, configured executable and bundled OpenCode launch contracts remain OpenCode-specific until a CAgent launcher has equivalent evidence. Each unavailable mode has a visible reason; selecting CAgent never installs or launches OpenCode as a fallback.

## One adapter implementation, bounded host integration

Preserve the existing caller-facing facade during incremental migration. Define domain contracts from actual consumers, not from an OpenCode SDK or the unknown CAgent schema. OpenCode adapters continue using their verified SDK boundaries. CAgent uses its own documented API behind a runtime-neutral adapter module executed by the trusted host: the web backend, or the VS Code extension host. Electron reuses its in-process web backend. Both hosts compose the same CAgent codecs and operation implementation with their existing transport/auth owners.

Shared UI calls explicit OpenChamber operations through existing runtime contracts; autonomous jobs use the same host operation dispatcher. CAgent credentials and wire payloads stay at that host boundary. Thin message/event bridges expose normalized results. Register explicit operations before generic OpenCode forwarding, and refuse OpenCode-only proxy paths while CAgent is selected. There is no separate sidecar, browser-side duplicate CAgent adapter, or proxy that pretends CAgent implements OpenCode URLs.

CA-01 freezes the concrete module map and migration inventory. Move only the protocol assumptions needed by consumed operations; avoid a repository-wide rename. Existing sync, persistence, queues and native ownership stay intact. The minimum contract groups are:

| Group | Required semantics |
| --- | --- |
| Identity and workspace | Backend identity, auth outcome, capabilities and the meaning of a remote workspace. Local paths are not assumed to identify remote CAgent workspaces. |
| Sessions and history | Opaque scoped IDs, create/list/read where supported, pagination, messages/parts and authoritative read failures. |
| Dispatch and activity | Inputs, attachments where supported, accepted versus completed, terminal errors, observable activity and cancellation capability. |
| Events and recovery | Typed domain updates, stable entity identity, authoritative reconciliation and explicit unknown outcomes. A tested status/history polling path may replace absent streaming; its latency and cost are declared. |
| Decisions | Permission/question delivery and replies with the documented semantics. Missing decision APIs never imply permission granted. |
| Configuration and tools | Separately gated catalogs, settings, credentials, MCP, plugins and reload. OpenCode config files and plugin formats never become CAgent defaults. |
| Extensions | Versioned CAgent-specific typed actions and results under the extension contract below. |

Do not manufacture token counts, costs, timestamps, completion, remote filesystem access or cancel success. If a required semantic cannot be supplied, its dependent feature stays disabled. Preserve opaque original IDs and use the existing runtime/workspace scope for collision isolation.

## Capability evidence and feature availability

The architecture owner produces a complete feature-to-operation dependency registry from current consumers, including browser-closed callers. Every current feature is classified as OpenChamber-owned, backend-dependent or mixed. Git/filesystem actions remain available only where their actual owning host has the required access; a remote CAgent workspace does not establish that access.

For each CAgent operation record one of `unverified`, `supported`, `adapted`, `unsupported`, with evidence, limitations and reason. Documentation can establish a candidate mapping or an explicit absence. Runtime acceptance establishes support for a particular adapter/server contract. A timeout, auth failure or 404 from an unverified path is a connection/contract error, not proof of permanent unsupported behavior. Keep temporary availability separate from compatibility support.

Effective feature availability is the intersection of verified operation support, declared semantic limitations, host implementation, current authorization and readiness. Freeze explicit all-of/any-of dependency rules where alternative implementations exist. Declaring `supported` in a manifest alone cannot enable a feature; the validator requires linked acceptance evidence. Runtime checks still run before side effects. Revalidate after adapter/server contract changes.

| Consumer | Required behavior when prerequisites are missing |
| --- | --- |
| UI controls, menus and shortcuts | Disable an existing feature with a useful reason in its owning UI; omit irrelevant settings and expose a capability summary. Shortcuts and deep links obey the same guard. |
| Queue, schedules, assist, goals and other autonomous callers | Reject new unsupported work; preserve existing intent as blocked with its reason. Do not consume, reroute or mark it successful. Unrelated work continues. |
| Core chat | Require identity/workspace binding, creation or binding of a documented conversation, dispatch and reliable outcome observation. History, attachments, stop and decisions each have independent gates. If the server can demand a decision that cannot be answered, the affected chat mode is disabled. |
| Missing stop | Disable Stop and unattended modes that require cancellation. An explicitly chosen interactive mode can remain available only if completion is observable and the UI states that cancellation is unavailable. Closing the view does not claim server cancellation. |
| Config, plugins, MCP, OAuth and reload | Disable each unsupported operation independently. Do not write OpenCode config, inject OpenCode plugins, migrate storage or call dispose against CAgent. |

No actual CAgent feature classification is possible outside the environment. The local capability report must distinguish proven unsupported operations from work not yet verified. The Legacy promise remains unchanged; CAgent may deliver a deliberately reduced feature set with explicit acceptance.

## CAgent-specific capabilities

Preserve capabilities whose semantics have no shared equivalent under a `cagent` namespace. Each extension declares its stable action ID, schema version, label/localization keys, context requirements, input/output schemas, effect class, authorization, cancellation and outcome semantics, and evidence references. IDs and field keys come from a generated constants module shared by registry and implementation.

CA-02 provides a finite renderer for text, numbers, booleans, choices and bounded lists as inputs, plus text, structured fields and tables as results. It supports read actions and explicit mutation actions with visible progress and unknown outcomes. The manifest selects only these fixed components and registered adapter handlers; it cannot contain JavaScript, HTML, executable expressions, arbitrary URLs or shell commands. Enforce schema limits, access checks and side-effect declarations at the host dispatcher, not only in the renderer.

A new operation that fits shared semantics uses the shared contract. A CAgent-only operation fitting the renderer becomes a namespaced extension without shared UI edits. An operation needing a new interaction model, binary handling or native privilege is recorded as `requires-host-development`, disabled and assigned to the architecture owner for a focused typed component/handler. Do not flatten an interactive workflow into a text action and lose its semantics. This route preserves future support without asking the weak agent to rewrite core UI.

For every delivered extension test input rejection, effect/permission checks, successful result parsing, failure/unknown outcome, backend switching and unavailable hosts. Unknown extension schema versions remain disabled. Extension availability is bound to the same backend identity and capability revision as core actions.

## Local agent constraints and validation

The kit freezes shared contracts, reference tests, feature dependency rules and extension schemas outside the writable adapter workspace. Supply one operation per task packet, with its relevant documentation excerpt, input/output examples, allowed files, fixed test command and completion rule. Generate the operation skeleton and registry rather than asking the model to invent architecture or symbols. Ambiguous documentation produces a specific evidence gap, not a guessed mapping.

Use deterministic mapping for simple methods/paths/fields. Custom typed codecs handle verified semantic differences. Both pass the same fixtures and host-level checks. Keep secrets out of mapping files and exported reports; runtime auth uses the existing secret owner. The kit works offline with its tested toolchain and dependencies; no package installation or online code generation is required inside the environment.

Enforce the editing boundary through the local runner's filesystem permissions, with shared contracts and reference tests read-only. A prompt listing allowed files is not enforcement. Before accepting a packet, the maintainer-owned runner compares protected artifact digests against the frozen kit and runs its own checks. Adapter code, model-written reports and adapter-provided test commands cannot redefine those checks. CA-02 must demonstrate rejection of a changed protected artifact as well as an out-of-scope source edit.

The architecture owner supplies negative fixtures and baseline tests; the local agent cannot satisfy acceptance by changing them. A changed-file allowlist check, schema validation, fixture replay and feature-coverage check reject edits outside the packet or unsupported capabilities marked enabled. Local fixtures alone are not sufficient: a local maintainer runs the real journeys against an isolated server workspace and signs the evidence report. These controls reduce model error; they do not make its self-reported tests trustworthy.

Dispatch ambiguity and directory disposal follow the [shared integration contract](OPENCODE-INTEGRATION-SPEC.md) and the evidence standard in the [Legacy dispatch contract](OPENCODE-LEGACY-1.2.27-SPEC.md). CAgent must independently prove any idempotency, result lookup or directory-dispose semantics. Legacy evidence cannot establish CAgent support.

## Host acceptance and priority

| Host | CAgent execution and acceptance |
| --- | --- |
| Web | Backend adapter plus authenticated shared operation routes; browser-closed jobs and UI use identical capabilities. |
| Electron | Same in-process backend; no CAgent credentials or protocol implementation in renderer/main copies. Verify desktop switching and quit ownership. |
| VS Code | Same adapter in extension host with existing dedicated message/event bridges. Until tested, the CAgent host option is explicitly unavailable. |
| Hosted mobile | Uses selected server's adapter and capability summary; verify touch extension forms and reconnect. |
| Capacitor | Uses selected OpenChamber host; no local CAgent process. Unsupported hosts remain disabled until a real connection journey passes. |

CA-00 freezes the consumed-operation and file ownership map. CA-01 implements host contracts and capability guards with current OC1/OC2 regressions. CA-02 delivers and tests the complete offline kit using both a deliberately sparse example backend and a backend with one synthetic extra feature; neither is claimed to be CAgent. CA-03 is the environment-local adaptation and real acceptance, including a capability report for every consumed feature and every newly discovered CAgent feature.

Only common baseline work INT-00 precedes this urgent sequence. CA-03 acceptance is the priority gate before the remaining INT implementation starts. If environment access/docs are unavailable, report that gate blocked and deliver the completed kit; do not silently start the lower-priority work. A maintainer may explicitly change that ordering. Final integration retains all Legacy and OC1/OC2 gates.
