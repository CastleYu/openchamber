## 2.1 侧边栏名称大小写

### 使用体验

建议规则：按保存的项目名称原样显示。没有自定义名称时，沿用现有文件夹名称推导逻辑，保留其大小写。
`OpenChamber`、`MyAPI`、`中文SDK` 在普通项目行、吸顶标题、最近项目和 worktree 分组中应保持一致。
会话标题继续保留用户输入的文字。

仅在受影响的名称显示位置移除强制大小写转换。保留现有路径规范化、项目 ID、排序、搜索匹配和去重规则。
显示大小写的调整不能重命名文件夹，也不能生成第二个项目。本项不改变共享 Button 的整体文字样式。

长名称继续截断，通过提示或现有无障碍名称提供完整文本。
重命名后，同一项目的各处显示都应更新，同时保留聊天组件和当前选中的会话。

### 验收标准

- 混合大小写、纯大写、纯小写、中文和自定义名称，在普通列表、吸顶、最近项目及 worktree 中保持原文。
- 重命名、搜索、选择和重复路径处理保持一致。
- 窄侧边栏及 200% 文字缩放下，长名称仍可使用。
- 重新加载后，项目身份和显示名称保持一致。

## 2.2 个人版本更新提醒

### 来源与版本标识

使用构建所配置的个人发布仓库。BUILD.md 当前记载 `CastleYu/openchamber`，实现前需与发布工作流核对。
仓库身份和发布策略由现有 personal-build 模块管理；桌面端与服务端共同需要的解析、比较逻辑放在共享辅助模块中。

BUILD.md 当前只比较社区版本。本文建议为个人构建替换这条规则：将版本解析为上游的 `major.minor.patch`
和个人版本的 `DIJIANG feature.fix`。历史单层个人版本按 `feature.0` 读取。
构建元数据不影响排序，调试构建不作为发布候选。

建议先比较上游数字版本，再比较个人数字版本。
即使候选版本的上游版本更新，只要其个人 `feature.fix` 低于当前安装版本，也排除该候选。
这样可避免因上游升级而推荐个人功能集更旧的构建。未来若有不同排序的发布分支，需要显式调整策略。

| 已安装版本 | 候选版本 | 预期结果 |
| --- | --- | --- |
| `1.23.0-DIJIANG.3.5` | `1.23.0-DIJIANG.3.6` | 有更新 |
| `1.23.0-DIJIANG.3.9` | `1.23.0-DIJIANG.3.10` | 有更新，按数字比较 |
| `1.23.0-DIJIANG.3.5` | `1.23.0-DIJIANG.4.0` | 有更新 |
| `1.23.0-DIJIANG.3.5` | `1.24.0-DIJIANG.3.5` | 有更新 |
| `1.23.0-DIJIANG.3.5` | `1.24.0-DIJIANG.2.9` | 排除，个人版本降级 |
| `1.23.0-DIJIANG.3.5` | 相同标识或更旧版本 | 无更新 |
| `1.23.0-DIJIANG.1` | `1.23.0-DIJIANG.1.1` | 有更新 |
| 个人构建 | 普通社区标签或调试标签 | 不属于个人发布候选 |

DIJIANG 标签使用 SemVer 预发布后缀，因此不能直接让 GitHub 的普通 latest-release 筛选决定候选资格。
建议读取仓库发布列表，从中选择已发布、非草稿且具有预期发布元数据的 DIJIANG 版本。
单独一个 GitHub prerelease 标记，不足以排除其他条件均有效的 DIJIANG 发布。
本文不扩展实验性更新频道。

限制请求时长和分页范围。如果达到限制时仍无法确定结果，应报告检查不完整。
部分列表、损坏的元数据、限流或网络失败都不能显示成“已是最新版本”。
更新说明和发布页链接必须对应最终选中的标签。

### 界面与状态

复用现有更新入口和对话框，显示完整已安装版本、候选版本、个人仓库和上次成功检查时间。
发现更新后的主要操作是打开对应发布页。HTTP、IPC、CLI 和包管理器路径继续执行“仅通知”约束。

| 状态 | 显示内容和操作 |
| --- | --- |
| 尚未检查 | 当前安装版本和“检查更新” |
| 检查中 | 轻量进度反馈；重复点击复用正在执行的请求 |
| 有更新 | 当前与候选版本、对应更新说明和“查看发布” |
| 已是最新 | 没有更新的合格个人版本，并显示检查时间 |
| 失败或不完整 | 明确错误和“重试”；旧结果保留并标注为上次结果 |
| 没有合格发布 | 说明未找到匹配的个人发布版本 |

保留现有检查频率。按仓库和候选版本去重通知，手动检查仍显示结果。
切换运行端时，旧请求的结果失效，不能覆盖新运行端的状态。
个人版本检查失败后，不自动改查社区 GitHub 发布或 npm。

### 跨端约定与验收

桌面端检查已安装的桌面构建。Web 和托管移动页面显示所连接服务器的版本，并明确标注其归属。
VS Code 和 Capacitor 需要区分已安装客户端与所连接服务器：只有发布源确实提供相应客户端产物时，
才展示该客户端的更新。Windows 便携可执行文件不能被描述为扩展或移动客户端更新。

测试版本比较表、损坏元数据、HTTP 失败、分页限制、重复检查和运行端切换后的过期响应。
使用真实打包桌面程序，配合受控的“有更新／已是最新／失败”响应验证对话框和发布链接。
重新检查直接安装入口的限制。在线仓库验证是独立验收步骤，本次设计未进行在线发布查询。
实际实施时同步调整 BUILD.md 和 REL-01 的约定。

## 2.3 工作中的会话呼吸效果

### 位置与外观

建议放在最外层会话容器，包围消息区域和输入区域。即使当前回复滚出视野，用户仍能看到工作状态。
使用一个不参与交互的装饰轮廓层，颜色固定取自主题的 `status.info`。
透明度在 0.25 和 0.65 之间往返变化，周期 2.4 秒，使用 ease-in-out。
这些数值是供视觉评审的初值，不是性能测量结论。

轮廓层沿用现有圆角，不占布局空间，忽略指针事件。
不得遮挡文字、滚动条、选择内容或焦点环。轮廓本身使用静态边框，仅动画化透明度。
因此不原样复用现有改变边框颜色的动画。现有 BusyDots 可以保留，用于在消息列表内指出正在工作的回复。

### 状态来源

通过现有会话状态约定，读取当前选中会话的权威实时状态，只订阅该指示器需要的字段。
不新增轮询定时器、token 计数器或持久化“工作中”标志。

| 当前可见会话的条件 | 表现 |
| --- | --- |
| 忙碌或重试中，且连接状态可信 | 显示呼吸效果 |
| 等待用户审批或回答 | 显示静态提示，现有操作提示优先 |
| 空闲、完成、取消或失败 | 移除呼吸效果 |
| 连接中断或活动状态未知 | 移除呼吸效果，由现有连接状态说明情况 |
| 其他会话忙碌 | 当前空闲会话不显示呼吸效果 |
| 窗口隐藏或会话组件卸载 | 不运行动画 |
| 开启减少动画 | 工作期间使用静态轮廓 |

先判断等待用户操作和断连状态，再判断 busy/retry。
切换会话时立即根据新会话计算表现。服务端任务继续运行，不依赖指示器是否挂载或可见。

### 验收标准

覆盖空闲 → 忙碌 → 重试 → 完成，以及审批等待、取消、断连、重连、忙碌与空闲会话之间切换。
检查浅色和深色主题、减少动画、键盘焦点、窄移动布局和展开的输入区域。
屏幕阅读器继续使用现有状态文本；装饰层不暴露给无障碍 API，也不逐次播报呼吸动画。

在相同生产构建场景中，对比启用与关闭指示器时的流式输出和会话切换。
每种情况记录三次可比采样，包括帧是否持续产生、p95 帧耗时、脚本及绘制成本。
指示器不得新增轮询请求或 JavaScript 动画定时器，不得由动画驱动布局计算，空闲或隐藏后应停止动画。
如果性能变化超出基线的正常波动范围，应在验收前解决。
只动画化透明度是设计选择，不能据此声称渲染成本为零。

## 2.4 添加项目

### 建议流程

原始需求没有说明当前具体哪里不好用。建议第一轮改善现有对话框的清晰度和失败恢复体验，
保留路径输入及补全、目录浏览、多选、创建目录和克隆仓库，所有支持的入口使用同一套对话框。

1. 从侧边栏、项目设置或命令面板打开对话框，显示正在浏览哪台主机的文件系统，明确本地与远端路径归属。
2. 输入或浏览到已有目录。提交前显示完整选中路径和项目名称；已存在的项目标记为“已添加”。
3. “创建文件夹”和“克隆仓库”保持为显式操作。已有路径无效时，不能自动转换成创建目录请求。
4. 提交一次。请求期间保留选中路径的显示，并抑制重复提交。
5. 全部成功后关闭对话框，按现有选择语义激活项目。多选时，建议以显示的选择顺序中最后一个成功项目为活动项目。
6. 部分成功时，分别展示成功与失败路径，保留对话框，仅重试失败项。在用户完成或显式打开成功项目之前，保持当前活动项目。

单个路径已经添加时，提供“打开项目”，避免重复添加。
项目身份判断沿用现有运行端的路径规则，包括所属文件系统的大小写敏感性。
名称显示遵守 2.1。

### 错误、取消与跨端行为

在选中项旁显示对应路径的错误，并保留用户输入。
如果现有 API 提供具体原因，区分目录不存在、权限不足、主机不可用和克隆失败；
否则展示实际返回的错误，不推测原因。Toast 可以补充反馈，但不能成为唯一的错误展示位置。

提交前关闭对话框，仅丢弃对话框输入。执行期间应如实说明现有取消能力。
关闭对话框不等于正在进行的克隆已经取消。
如果克隆或目录创建成功，但项目登记失败，应显示已经创建的路径并提供重新登记操作。
保留已创建的数据；重试不能盲目重复克隆或创建第二份副本。

Web、桌面端、托管移动页面和 Capacitor 浏览所连接服务器的文件系统。
桌面端只有在本机选择器指向同一文件系统，或存在显式支持的路径映射时，才提供原生选择器。
VS Code 通过扩展宿主添加工作区文件夹，并以返回的权威结果生成项目。
能力不可用时，应在界面上明确体现。

### 无障碍与验收

复用共享对话框、输入框、列表和按钮组件。每个路径输入框都有无障碍标签。
支持共享的方向键和 Ctrl+N/P 导航、输入法、可见焦点，以及关闭后将焦点还给原入口。
现有移动端弹层和触控目标保持可用。
本设计没有新增设置页或持久化偏好，因此无需新增设置布局或搜索条目；
如果实施时移动了已有可搜索操作，再核对设置搜索。

验证单选、多选、已添加路径、大小写变体、非 Git 目录、缓慢远端浏览、权限失败、部分成功、重试，
以及“克隆成功但登记失败”。同时验证键盘与触控流程。
最终可见项目列表必须与成功登记结果一致，活动项目遵守单选和多选规则。
