# Token 过度消耗分析

日期：2026-09-26  
任务：OpenChamber OC1 与 OC2 双内核兼容交付  
统计截止时间：2026-09-26T07:55:24.371Z，即 Goal 标记完成的时间

## 结论

本次任务超出预期，主要原因是少数长期运行的代理携带不断增长的上下文，执行了数千次模型调用。缓存本身工作正常，98.39% 的输入 token 命中了缓存。真正的问题是调用次数过多，而且每次调用都会增加新的上下文。

统计共找到 98 个关联会话文件、7,237 条唯一模型用量记录，覆盖主代理、48 个协作子代理和 48 个 Guardian 自动审批会话。没有重复的 response ID。

所有模型处理的原始总量是 1,171,249,263 token，其中绝大部分是缓存输入。用于分析新增工作的口径是未缓存输入加输出，共 21,411,567 token。排除 Guardian 后是 17,720,033 token。

Goal 工具报告的用量是 15,831,548 token。这个数既不等于模型原始 token，也不等于未缓存输入加输出。会话日志没有记录 Goal 计数的权重公式，因此本报告不把它当作计费总量。

## 统计口径

| 指标 | 定义 | 本报告中的用途 |
|---|---|---|
| 输入 | 模型调用报告的全部输入 token | 衡量模型读取的上下文总量 |
| 缓存输入 | 由提示缓存提供的输入 token | 衡量上下文复用量 |
| 未缓存输入 | 输入减去缓存输入 | 近似衡量每次调用新增的输入 |
| 输出 | 模型输出 token | 已包含推理输出，不重复累加 reasoning token |
| 原始总量 | 输入加输出 | 衡量未套用缓存价格前的全部模型处理量 |
| 增量用量 | 未缓存输入加输出 | 用于诊断新增工作，不是计费公式 |
| 缓存率 | 缓存输入除以输入 | 按 token 加权的缓存复用率，不是命中缓存的请求比例 |

## Guardian 开销

Guardian 不负责产品代码。它审核需要提权的 Git 写入、网络与依赖操作、原生应用启动、进程与注册表操作，以及 Release 操作。

48 个 Guardian 会话产生了 3,656,447 个未缓存输入 token，输出只有 35,087 token，输入与输出比例约为 104:1。每次审批通常都收到较大的任务和权限上下文，其缓存率也低于实现代理。

解决方法不是绕过审批。主代理应减少需要单独提权的操作数量，在合适时使用稳定的已批准命令前缀，并把相关操作组织成一次可明确审核的窄命令。

## 根因

### 1. 模型轮次过多

本次任务产生 7,237 次模型响应。平均每次响应新增约 2,594 个输入 token 和 365 个输出 token。大量小工具操作不断跨越模型调用边界，累积成主要开销。

### 2. 长期子代理反复接收无关的新任务

高消耗子代理没有在原任务结束后关闭。主代理继续给它们追加实现、排障、验证和文档任务。稳定缓存前缀不断增长，每条新命令都携带此前积累的完整上下文。

### 3. 主代理微观管理执行过程

主代理逐次读取结果、转发进度、要求修正并轮询状态。许多工作本可留在边界明确的子任务中，或者由一个验证代理一次完成。

### 4. 所有阶段放在同一个 Goal 中

研究、设计、实现、测试、原生验收、发布和发布后的关闭诊断共用一个任务。主代理上下文从未回到较小的基线。

### 5. 没有用量限制

Goal 没有 token 预算，子代理也没有模型调用上限、follow-up 上限和最大重试次数。Goal 自动续跑只关注完成任务，没有成本停止条件。

### 6. 高等级模型承担机械工作

主代理大部分协调阶段持续使用 Astra。Sol 承担了全任务 64.0% 的原始处理量。命令执行、测试、fixture、状态检查和文档任务在架构确定后大多可以交给 Luna。

### 7. 可发布状态之后仍继续扩大验证

部分后期验证是必要的，但缺少停止规则。原生关闭问题很显眼，却不是主要开销。三个 portable 和 shutdown 子代理的增量用量合计 404,209 token，只占总量约 1.9%。此前的定性分析高估了这部分影响。

## 下一次上游更新的控制措施

### 拆分任务生命周期

使用独立任务处理以下阶段：

1. 上游与接口盘点；
2. 架构与任务审核；
3. 实现；
4. 集成与运行验证；
5. 提升分支与发布。

每个任务从精简的交接文档开始，不复制此前的完整会话。

### 限制每个子代理的范围

每次委派必须明确一个负责范围、允许修改的文件、一次验收命令集和停止条件。代理提交最终结果后立即结束。即使旧代理处于空闲状态，新功能也使用新代理。

建议限制：

| 项目 | 上限 |
|---|---:|
| 普通固定范围子代理 | 40 次模型调用 |
| 复杂实现子代理 | 150 次模型调用 |
| 每个子代理的 follow-up | 1 次 |
| 同一失败的验证重试 | 2 次 |
| 每阶段主代理模型调用 | 200 至 300 次 |
| 每阶段主代理命令调用 | 100 至 150 次 |

超过限制后，代理应返回阻塞点和证据。主代理再决定是否建立新的短上下文任务。

### 减少协调消息

子代理只报告阻塞、方向发生实质变化或最终结果。主代理不回复不会改变下一步行动的进度消息。等待多个代理时使用一次有界等待，不频繁查询状态。

### 批量执行工具操作

互不依赖的文件读取、Git 检查和测试结果检查应放进同一次工具调用。验证代理执行约定的全部命令并返回一份结构化结果。主代理只复跑存在争议的证据。

### 按阶段选择模型

| 工作 | 模型 |
|---|---|
| 架构和一次最终跨模块审核 | Astra |
| 复杂实现与排障 | Sol |
| fixture 迁移、测试、文档、打包和 CI 观察 | Luna |

只在阶段边界切换模型。大型上下文中反复切换模型可能造成缓存冷启动。

### 设置明确预算

下一次相似任务应在创建 Goal 时设置预算，并分配到各阶段。可以先以 800 万 Goal 计量 token 为目标，在 50%、75% 和 90% 时进行成本检查。检查时先删除重复验证和协调工作，不削减必要的产品范围。

## 预计节省量

下面根据本次每次调用的平均增量 token 粗略估算，不代表价格承诺。

- 如果主代理从 1,377 次调用降到 300 次，按相同平均增量计算，可节省约 350 万 token。
- 如果三个最大实现代理分别限制在 150 次调用，并将后续工作拆成新的短任务，可节省约 440 万 token。
- 如果通过减少单独提权操作，把 Guardian 冷上下文开销降低一半，可节省约 180 万增量 token。

这三项可把 2,141 万增量用量降到约 1,160 万。要回到原先接近 800 万的 Goal 预期，还需要进一步拆分阶段、批量运行工具和收紧模型选择。
