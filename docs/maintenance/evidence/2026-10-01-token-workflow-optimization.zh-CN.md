# 上游引入工作流优化

日期：2026-10-01
对象：DIJIANG 4.1 上游引入的那一轮执行，时间为 2026-10-01 01:33 至 07:33（UTC+8），因 Codex 周额度耗尽而中止。
English: [2026-10-01-token-workflow-optimization.md](2026-10-01-token-workflow-optimization.md)

## 结果

根据估计，下面的工作流改进可将相同范围运行的原始输入 token 减少 57%，加权使用量减少 48%。保守估计下，减少幅度分别为 50% 和 41%。大部分收益来自两项改动：降低自动压缩阈值和为子代理使用短暂的单任务生命周期。

## 静态估计

模型：原始输入 ≈ 调用数 × 平均上下文。在压缩之间线性增长时，平均上下文约为 (残留 + 触发) / 2。每次压缩读取一个完整窗口，使下一次调用缓存缺失。删除的调用大多是轮询和消息，每个计为平均新鲜输入和输出的一半。

实际测量输入：残留 52k，增长 1,200 token/调用，旧触发 320k，新鲜输入 1,682 token/调用，输出 346 token/调用。

杠杆假设：

- A. 压缩触发在 160k。
- B. 调用纪律：空轮询减少 80%，消息减少 85%，15% 的 shell 调用通过分批合并。
- C. 分组提权：Guardian 会话减少 80%。
- D. 主代理无重复验证（减少 200 次调用）和摘要测试输出（每次调用新鲜输入减少 20%）。

价格加权假设缓存输入成本为未缓存输入的 0.1 倍，输出成本为未缓存输入的 8 倍。这是通常的 API 价格比率。帐户实际 Codex 信用加权未在日志中显示。根据此加权，缓存输入占基准成本的 79%。

| 场景 | 调用 | 原始输入 | 未缓存 + 输出 | 加权 |
| --- | ---: | ---: | ---: | ---: |
| 基准（模型检查） | 5,766 | 1,070.6M | 14.97M | 134.3M |
| 仅 A | 5,766 | 613.4M (−42%) | 16.88M (+13%) | 90.3M (−32%) |
| A + B + C | 4,231 | 454.4M (−57%) | 12.78M (−15%) | 68.9M (−48%) |
| A + B + C + D | 4,031 | 431.4M (−59%) | 10.39M (−31%) | 64.2M (−52%) |
| A + B + C，保守 (B 70%/70%/0%, C 60%) | 4,951 | 530.4M (−50%) | 14.34M (−4%) | 78.8M (−41%) |
| 仅窗口重置 (≈245k 触发) + B + C | 4,231 | 631.2M (−41%) | 11.71M (−22%) | 85.7M (−36%) |

限制：

- 降低触发点增加压缩次数，从 25 到约 47，每次压缩缓存缺失一次。除非 B 和 D 也适用，否则新鲜 token 使用量上升。
- 估计保持相同的产品范围。推迟 37 个后期提交会将其成本转移至下一批次；不会消除成本。
- 将两个 Sol 子代理移至 Luna 不改变 token 计数。仅在帐户对模型加权不同时降低成本，且日志无法显示这一点。
- 固定的单次调用上下文约 43k token。已安装技能列表约占 31k 字符，记忆摘要约占 13k。此估计不会减少该部分。

## 未应用：维护人员操作

这些设置改变每个项目的批准或插件行为，需要维护人员自己决策。

- 批准规则。向 `~/.codex/rules/default.rules` 添加窄 `prefix_rule` 条目，用于此引入必须提权的命令，如 `["git", "fetch"]`。不允许通用 `node` 或 `bun` 前缀；按阶段分组这些提权。
- 插件。禁用此仓库中从不使用的插件，如 Vercel、Slack、Linear 和 Gmail 包，会缩小每次调用加载的技能列表。
