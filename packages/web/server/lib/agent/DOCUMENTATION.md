# Agent dispatch contracts

Extension input, receipt, result-envelope and snapshot wire schemas now live in
`schemas.js` for host and browser reuse. The host still parses manifest-specific
values through `extensions.js`. The shared client checks exact identity, declared
context, bounded results and receipt semantics without importing host I/O. Client
parsing grants no authority and does not provide durable extension recovery.

This module implements part of CA-01. The server reserves authenticated owned routes, but its binding remains inactive and CAgent is unavailable. Current OpenCode runtime behavior is unchanged. The remaining migration is tracked in [the execution checkpoint](../../../../../docs/maintenance/CAGENT-EXECUTION.md).

`constants.js` owns backend-family, support, operation and refusal constants. `dispatcher.d.ts` defines runtime-neutral requests/results for the 22 effect/read operations consumed by the host inventory. Identity capture is the 23rd host operation and belongs to the dispatcher rather than the adapter. Workspace IDs are backend-owned identifiers, never implicit local directories. No SDK raw payload is required by these contracts. More detailed message/decision contracts and UI operations must be added from consumer semantics before their migration is accepted.

`extensions.js` owns strict finite CAgent extension manifests and value parsers. Inputs are bounded scalar controls or scalar lists; outputs are text, fields or tables. Manifest metadata has no activation authority. The offline kit shares this schema and a synthetic refusal template. Protected host registration and dispatch now exist; adapter assembly, shared UI controls/renderers and real acceptance remain incomplete. Production extensions stay unavailable on all five runtimes.

`createAgentAuthority` accepts up to 64 unique optional extension registrations, each with a detached frozen manifest, capability evidence and host handler. Optional independent approval rows bind action ID, manifest revision and `agentExtensionDigest(manifest)` in addition to the existing connection/server/adapter/artifact requirements. The digest hashes JSON serialization of the parsed canonical manifest. Old approvals without extension rows grant no extension. A failed action row does not remove unrelated accepted actions. This is host registration, not permission for the environment-local author to edit host code.

`extension-runtime.js` enforces current CAgent identity and a verified principal before enumeration or dispatch. GET `/api/agent-backend/extensions` returns finite manifests and per-action availability. POST `/api/agent-backend/extension-dispatch` accepts action ID, exact identity and a strict input envelope. Required workspace/session context must be supplied; undeclared context, fields and read request IDs are refused. Reads return parsed finite results and cannot return mutation receipts. Mutations require a request ID, durable reservation and a matching accepted/complete/unknown receipt. An observed-outcome manifest requires a complete receipt; accepted-only does not imply completion. Approval is checked before effects and after results. Revocation before handler entry records not-sent; entered failures or malformed results retain unknown outcome. No prompt, values or result is persisted in the attempt ledger. The existing attempt lookup reads extension history without replay. Version-1 records additionally accept validated namespaced action IDs; existing core records retain their format.

Web, Electron, hosted mobile and Capacitor share these owned HTTP routes. VS Code retains its namespace refusal. This entry does not implement a cancellation UI or independently verify backend cancellation semantics. Synthetic HTTP and native storage tests prove the host boundary, not real CAgent API support.

`createAgentDispatcher({ getBinding, attempts })` reads host authority at call time. The adapter supplies handlers and candidate support; a separate host-owned acceptance record grants access for an exact adapter and capability revision. A supported declaration without evidence and matching acceptance is refused. Unverified, unsupported, auth failure, not-ready and missing-handler outcomes remain distinct.

`schemas.js` strictly parses inputs and outputs for all 22 operations. Dispatch passes the parsed request copy to the handler and returns the parsed result copy. Missing identifiers, invalid enums and extra keys are rejected. It captures backend identity and checks it again before entering a handler. After an identity change, reads reject stale data. An entered mutation reports an unknown outcome if its handler fails, its result is malformed, or the identity changes. Read failures without an identity change propagate to the owning boundary. This module performs no retry, fallback or cross-backend replay. Production mutations still require an accepted binding and migrated consumers.

Messages now carry a session ID and ordered parts instead of a flattened text field. Text preserves synthetic/ignored markers; reasoning remains separate; tools preserve call identity, typed lifecycle, JSON inputs and results. A completed tool requires an explicit result, including null when documented. A failed tool requires a normalized error. Attachments carry an opaque host asset ID, MIME and optional filename, with no direct URL field. The contract does not resolve assets or grant filesystem/network access. The host must add an authenticated asset owner before attachment display or dispatch becomes available.

Message state includes unknown and interrupted. Created/completed times, parent, agent/model selection, summary, finish, errors and usage are optional observations, not fabricated defaults. Times use Unix milliseconds. Token fields are nonnegative integer counts; cost is a verified USD amount and is omitted when the adapter cannot establish that unit. Error/finish values are normalized enums, not SDK error names. Missing chronology, model selection or usage must disable any dependent unattended behavior or accounting rather than supply invented values. This checkpoint does not migrate the existing UI model or goal runtime, which still have OpenCode assumptions; question/form, shell and other specialized message workflows also need their own consumed contracts before support can be declared.

Permission choices now have an opaque choice ID, display label, allow/deny outcome and once/session/persistent scope. Lists must be nonempty with unique IDs. Adapters map only documented scopes; an unsupported scope cannot be promoted to persistent approval. Reply still carries the selected choice ID. Current schemas do not establish that a reply belongs to a live pending permission; the actual decision consumer must validate it against the current request during migration. Message read results must match the requested session and, for a single-message read, its ID. A mismatched synthetic insertion result is unknown outcome after effect. Imports reject mixed workspace/session ownership before handler entry.

`createAgentDispatcher` now accepts a host-owned `attempts` store. All 11 mutation inputs require a request ID. Without storage, mutations are refused before entering a handler. `attempts.js` exclusively reserves an intent file and syncs its unknown record before dispatch. The key uses backend family, connection ID, optional host principal and request ID; epoch or adapter revision changes cannot permit resend of an existing intent. Concurrent reservations have one winner. Storage failure prevents dispatch and retains any incomplete reservation.

After reservation, the dispatcher rechecks authority. Revocation before handler entry records `not-sent`. Entered handler failures, malformed or mismatched receipts, unknown receipts and failed final persistence return `unknown-outcome`. Confirmed results record `accepted` or `complete`; acceptance does not establish completion. Final authority is rechecked after persistence. The ledger stores identity, operation, request ID and attempt state, without prompts, credentials or results. A restarted reader returns the recorded history, never live activity. Corrupt and unavailable storage are errors, not missing records. There is no automatic resend, deletion or retention policy. Native file sync is tested for process restart; power-loss durability and Windows ACL isolation are not established by these tests. Production composition supplies a lazy store under its existing data directory; no record is created without an accepted dispatch.

`readAttempt(expectedIdentity, requestID)` is host-owned history access, separate from the adapter operation inventory. It requires an authorized, ready binding and exact current identity before and after reading. A changed identity or revoked access rejects the result. It does not require current write capability, so a disabled operation can still have its recorded attempt inspected. The record retains its original epoch and revisions. A missing record returns explicit null; storage errors propagate. This lookup does not query CAgent or prove that an accepted request completed.

Host composition must supply normalized, immutable bindings. It must keep activation records and handler registration outside the environment-local agent's writable files. A manifest cannot construct this authority directly. Each handler must also parse its real server's response before projecting domain data. These schemas validate the neutral contract, not undocumented CAgent wire semantics.

`createAgentAuthority({ registrations, getSelection, getAcceptance })` now constructs those immutable bindings. Protected host composition supplies the registry and both synchronous read ports. Registrations bind backend family, adapter ID/revision, capability revision, artifact digest, candidate capabilities and callable handlers. Duplicate tuples or malformed registrations fail construction. Selection binds the current connection/epoch, tested server revision, readiness and authorization. Invalid or unregistered selections return no binding; unavailable host ports raise a fixed refusal. Authorization and readiness remain distinct for dispatcher checks.

Approval is an independent host record, never a field in the candidate manifest. It must match family, connection, adapter ID/revision, capability revision, server revision and artifact digest, and include nonempty evidence for each operation. Malformed, missing or mismatched approval grants nothing. Valid approval rows grant only candidate operations with supported/adapted evidence and a registered handler; an ineligible operation does not remove unrelated valid rows. Each read rechecks the host ports; an unauthorized or unready selection never reads approval storage. All binding metadata, capability evidence and operation lists are frozen copies, so later source edits cannot alter an in-flight snapshot.

Authority compares a host-supplied digest; it does not itself hash files or verify evidence artifacts. No public route, user setting or adapter workspace can supply these ports. Production supplies the read-only approval port and the initially inactive host coordinator below, so activation is still unavailable. A trusted adapter's executable handlers are not sandboxed by this metadata boundary. Protected runner enforcement and composition, selectors and consumer migration remain required before activation.

`createAgentHost` owns selection lifetime and composes immutable loading, current-connection transport, independent approval, durable dispatch and feature checks. Construction performs no I/O. Maintainer-only `select` validates the profile/connection, retires the old binding and allocates an epoch before asynchronous loading. Failure leaves the host inactive; it never silently restores or replays old work. A later selection or `clear` invalidates an earlier load, which cannot replace the newer binding. Each factory's request port expires with its selection, including when revisions are reused. Loading factories have no current connection. After loading, only independently approved operations can dispatch. Credentials remain in the host, and selection returns only the frozen neutral identity.

The coordinator validates structural inputs and verified artifact bytes, not server identity or acceptance evidence meaning. Readiness, authorization, endpoint and server revision come from protected maintainer composition. Endpoint/auth changes require another selection and therefore a new epoch. Candidate code receives neither `select`, `clear` nor approval-writing ports. Production routes now consume this coordinator's dispatcher/features, and trusted process startup can select a reviewed candidate. No user selector or protected runner is provided yet. All five runtimes retain unsupported feature behavior. Native `host.test.js` joins actual temporary artifacts, persisted approvals and loopback HTTP, including revocation, failed/overlapping loads and a cleared in-flight read. These synthetic journeys do not establish real CAgent compatibility.

`createAgentApprovals({ directory })` reads strict version-1 records from a host-owned directory. `agentApprovalName` hashes the family/connection tuple into an opaque basename. Each binding check reads one file, bounded to 64 KiB, without caching approval. Missing records return null; malformed JSON/UTF-8, extra fields, invalid evidence and scope mismatches fail closed. Linked roots/files, non-files and observed read-time changes are refused. The reader returns detached frozen approval rows and exposes no mutation methods. Unready or unauthorized selections return before filesystem access.

The protected runner must own the directory permissions and write reviewed records outside the weak Agent's writable workspace. The reader does not enforce Windows ACLs, validate evidence meaning or grant code isolation. Production points it at `agent-approvals` under the existing data directory. Construction performs no filesystem access or creation; the inactive selection cannot read that directory. Deletion or replacement takes effect on the next authority check, including the check after a handler returns.

`createAgentApprovalWriter({ directory })` is a separate maintainer-only port. The owner creates and protects the directory before use; construction performs no I/O. `write(approval)` validates the complete reviewed contract and serialized 64 KiB bound before accessing storage. It creates an exclusive same-directory temporary file with owner read/write mode, writes and fsyncs it, closes it, then atomically replaces the scope's record. Failure before replacement preserves the prior record and attempts temporary cleanup. It refuses linked/non-file roots or targets. `revoke({ family, connectionID })` removes only that scope, returning false for a missing record in an existing directory. Storage errors expose fixed codes.

The writer validates record structure, not evidence meaning or artifact provenance. Only an independent maintainer-owned runner may call it after verification and review; never pass it to candidate code. No HTTP activation/writer route is registered. The owning runner must serialize maintenance calls and enforce directory permissions. File fsync and rename do not establish Windows ACL isolation or power-loss durability of directory metadata. Native writer tests cover reader restarts, scope isolation, replacement, revocation, invalid-record preservation and authority checks. Runner composition remains outstanding.

`artifacts.js` provides read-only verification of a dedicated artifact snapshot against a host-protected manifest. The versioned manifest lists each portable relative path, byte length and SHA-256 digest. Its aggregate digest includes the sorted path/length/digest tuples. Validation rejects aliases, unsafe paths and excessive file counts or sizes. Verification refuses unlisted files/directories, symbolic links and junctions, missing files, digest/length differences and observed changes during reads. Hashing reads bounded chunks. Fixed errors expose neither artifact contents nor filesystem paths.

`agentArtifactDigest` helps generate a candidate manifest; a model-generated digest grants no trust. The host owns the expected manifest. `verifyAgentArtifacts` performs no import, activation or write. `readAgentAdapterArtifact` captures the fixed `adapter.mjs` entry during the verified read and returns an immutable source URL. `loadAgentAdapter` imports that captured source without reopening its original path. Verification is not a filesystem sandbox. Evidence meaning, independent approval and actual CAgent semantics require their separate checks. Native file tests and contract compilation cover these module boundaries.

The host-only loader accepts a protected CAgent profile and manifest. The single bundled entry exports only `createAdapter(context)` and returns strict operation capabilities and handlers. The host supplies adapter identity, revisions and the verified digest; candidate exports cannot override them. The factory receives a frozen JSON request port with relative paths, explicit methods, optional query/body and mandatory current runtime identity. It cannot pass origins, headers or credentials through that port. The transport owner must check the current connection/epoch and supply authentication at each call. HTTP status and JSON body remain explicit for the adapter to interpret against documented semantics. Binary and streaming contracts are not implemented by this port.

Loading runs reviewed native code with host privileges. It grants no operation approval and provides no process sandbox. Bundle helper imports into `adapter.mjs`; each factory invocation must own its state because Node caches the imported module. Keep source URLs out of routes and logs. The host coordinator composes loading and transport; trusted process startup provides selection, while protected approval runner enforcement and host feature support remain outstanding. Loading alone does not activate CAgent features. `loader.test.js` covers captured-byte imports, strict exports, independent approval, request validation and separate factory contexts using synthetic APIs.

`createAgentTransport({ getConnection })` supplies the native JSON HTTP port for the loader. The protected host port returns current CAgent identity, a canonical HTTP(S) API base URL ending in `/`, headers, authorization and readiness. Endpoint or credential changes must advance the epoch. Every request parses the current connection, checks the full expected identity and preserves the API path prefix. Candidate input cannot supply headers or origins. GET bodies, path normalization and encoded path separators are refused. Query values and JSON bodies are serialized explicitly; the host supplies JSON Accept/Content-Type headers.

The transport never follows redirects or retries requests. It checks identity/readiness/authorization after headers and after reading the body, refusing stale results and cancelling unread bodies where possible. A non-redirect HTTP error with valid JSON remains an explicit status/body for the documented codec to interpret. Status 204/205 has a null body; invalid JSON is a fixed refusal rather than empty success. Transport exceptions expose only fixed codes. This port does not itself grant operation approval or implement streaming or binary transfer. The host coordinator supplies the connection port, which remains inactive in production. `transport.test.js` uses native loopback HTTP servers and a verified sample adapter to test the complete read chain; it does not contact a real CAgent server.

The host-owned `timeoutMs` defaults to 30 seconds and accepts positive integers up to five minutes. Its deadline covers response headers and the complete JSON body. The optional third `request` argument accepts only a native `AbortSignal`; the loader validates and forwards it without serializing it into a wire payload. A pre-aborted signal refuses before HTTP. Each request combines its own deadline and caller signal, so cancellation does not poison subsequent requests. Fixed transport errors distinguish timeout and caller cancellation without exposing abort reasons. Owned routes return 504 for timed-out reads and 409 for cancelled reads. Once a mutation handler has entered, either failure remains a durable unknown outcome, with duplicate dispatch refused. Cancelling the HTTP wait does not prove backend cancellation, and no server Stop capability is granted. UI/HTTP-disconnect signal propagation and documented server cancellation remain separate unfinished consumer work.

The coordinator also supplies a host-owned `selectionSignal` to each transport. Clear, a structurally valid new selection and explicit OpenCode selection abort the retired signal before asynchronous loading. Held headers and incomplete JSON bodies stop without waiting for the server or the deadline. A retired port refuses before HTTP with `backend-changed`; retirement takes precedence over caller cancellation or timeout. Each later selection has an independent controller. An entered mutation remains unknown in the durable ledger, and reselection cannot replay its request ID. Only requests using the provided transport are covered; arbitrary native adapter work is not sandboxed or forcibly terminated. No production selector or server Stop API is added by this lifetime control.

`routes.js` owns GET `/api/agent-backend/runtime`, POST `/api/agent-backend/dispatch` and POST `/api/agent-backend/attempt`. Server composition registers the informational selection route first, then runs runtime, feature, dispatch and attempt requests through `resolveVerifiedAuthContext` on the UI auth controller. A valid explicit bearer determines the principal; an invalid bearer never falls back to a cookie. URL tokens are refused. A trusted client ID or validated password-session cookie becomes an opaque `principal-<SHA256>` identity. Missing verification or anonymous passwordless access cannot use these core routes; a valid trusted-client bearer remains eligible. Cookie changes take effect on the next request. There is no account model. Ordinary OpenCode routing is unchanged. The internal dispatcher may still be used without a principal by trusted host code; HTTP requests always use a principal-scoped dispatcher.

Dispatch and lookup require an exact expected identity. Both POST routes own their JSON parsers. Lookup carries the request ID in its strict body, never a URL. The routes expose fixed host-owned refusal codes instead of exception text: duplicate attempt 409, corrupt/unavailable storage 503 and entered unknown outcome 409. Unknown paths and methods terminate inside this namespace. Accepted bindings can dispatch durable mutations through the same host guard as direct callers. Without a store, accepted writes return `write-unavailable`. The current production dispatcher has no binding, so verified requests return `unavailable`; requests without a verified principal return `unauthorized`. No activation setting or adapter manifest can change that yet.

Old unscoped host attempts remain on disk but are not adopted into principal-scoped records. Former credential-derived browser journals are likewise retained without adoption. A verified client ID keeps its namespace across credential rotation. Re-pairing issues a new client ID and therefore a new principal; it does not recover the old device's journal. There is no account model. Remote CAgent credentials remain in protected host connection configuration and do not establish per-principal authorization at the remote server. Production CAgent support remains unavailable, and no real API acceptance has been performed.

`describeRuntime()` provides a snapshot for capability display: the identity plus availability/refusal for every one of the 22 operations. It reads one immutable binding, reuses dispatch eligibility and includes the durable-storage requirement for writes. It invokes no handler and returns no adapter evidence, reason text, credentials or wire payloads. The authenticated GET runtime route validates this complete response before serialization. A snapshot is informational; dispatch always checks current authority again. Feature dependency rules and UI/autonomous consumers must still be migrated before their availability can be derived from it.

`features.js` owns 17 fixed action dependency rules covering the current 22-operation inventory. All-of rules require every operation and prerequisite read. Session acquisition accepts either verified creation or reading an existing session. An optional action's failure leaves unrelated actions available. These rules are not the complete product registry. Queue, goals, sync, assets, decisions beyond permissions and CAgent extensions still need their consumed contracts and rules.

`createAgentFeatures({ getRuntime, getHostSupport })` intersects current operation availability with host-owned implementation support bound to the exact identity. Its optional support port defaults to null. Missing, malformed or duplicate implementation rows close all actions with `unmigrated-consumer`; a throwing port refuses availability, and stale identity is `backend-changed`. Candidate adapters cannot supply this port or replace the frozen rules. Production supplies no implementation port, so it asserts no actual caller migration.

`requireFeature(feature, expectedIdentity)` rechecks both ports on every call. Consumers must check before taking queued intent or entering a workflow, then use guarded operation dispatch. This is not a lease and executes no effects. Direct operation guards remain; actual UI, shortcuts and browser-closed callers are not yet migrated to feature checks. Prompt/status availability alone cannot prove interactive chat or unattended completion semantics.

The fourth owned route, GET `/api/agent-backend/features`, returns a strictly validated complete feature snapshot after authentication. It invokes no handlers and sends fixed refusal codes. Missing composition returns 503; production's inactive dispatcher also returns 503 `unavailable`. VS Code refuses it with the existing namespace guard. Feature snapshots provide information and grant no later dispatch authority. `features.test.js` and the feature HTTP tests check dependencies, alternative acquisition, host migration, identity, revocation and handler isolation.

## Shared HTTP contracts

`schemas.js` owns dispatch, attempt lookup, persisted attempt, attempt state and
fixed error schemas. Routes and durable storage reuse those schemas;
`schemas.d.ts` exposes precise operation-specific types for the shared UI
client at `packages/ui/src/lib/agent/client.ts`. Browser imports use only Zod
and Agent constants. The client parses complete snapshots and normalized

## Backend family selection

Authenticated GET `/api/agent-backend/selection` reads the protected host
`getSelection` port independently of adapter/runtime binding. Production server
composition supplies this port. The exact response is `{ family, revision }`,
with OpenCode or CAgent family and a nonnegative safe integer host revision.
It excludes credentials, connection details, adapter files and feature grants.
Missing composition returns 503 `unavailable`; malformed values or unexpected
callback errors return fixed 502 `backend-failed`. The route has no cache and
never invokes a handler or falls through to OpenCode.

An explicit failed CAgent load remains selected CAgent, even while runtime
inspection refuses an unavailable binding. OpenCode selection must be explicit.
The shared client can read this descriptor before inspection. App root gating
is still unfinished, so this route does not establish UI or CAgent acceptance.
Web, Electron and both server-connected mobile runtimes share this composition.
VS Code keeps the owned namespace's 501 `unsupported-runtime` refusal.

`startWebUiServer` accepts an optional maintainer-only `agentBackend` startup
option. `selectAgentStartup` strictly validates its family and reviewed artifact
candidate before any lifecycle or persisted consumer starts. Omission selects
OpenCode. Explicit CAgent failure propagates and never falls back to OpenCode.
This programmatic composition input is not an HTTP, settings or adapter port.
It validates structure and artifact bytes, not server identity, readiness or
acceptance meaning. The maintainer must supply and independently verify those
inputs. Host feature support is still absent, so selection does not enable chat.

`startOpenCodeConsumers` starts automatic permissions and the message queue only
for the current OpenCode selection. Selection retirement stops both. Queue stop
preserves queued items and rejects a send after a pending idle check completes.
Already entered mutations are not canceled. These are process startup ports,
not a complete hot switching flow. Subsequent backend use requires a fresh
explicit startup and its independent approvals.

The coordinator defaults to OpenCode and exposes an immutable `getSelection()` snapshot with family and revision. A structurally valid CAgent selection advances that revision before loading; loading failure and `clear()` retain the CAgent family with no active binding. Only the maintainer-owned `selectOpenCode()` port returns to OpenCode. It also retires pending adapter loads and selection-scoped request ports. Snapshots contain no credentials, perform no I/O and remain unchanged after later selections.

The web entrypoint composes one coordinator for the Agent routes and OpenCode kernel runtime. Its selection port invalidates the OpenCode descriptor by family/revision, including a same-endpoint return. CAgent produces an unsupported descriptor and performs no OpenCode generation probe. Concurrent refresh and health probes share valid results; descriptor commits alone do not retire a connection. Tests join the real host with the kernel runtime and native adapter artifacts. Production still has no user selection entrypoint or host support approval; CAgent remains unavailable on all five hosts. This gate covers descriptor consumers, not every unmigrated owned route, lifecycle action or UI caller. Their individual migration remains required before activation.

## OpenCode lifecycle isolation
The Web lifecycle and readiness loop now consume the same family/revision
snapshot. CAgent skips OpenCode bootstrap and monitoring; direct OpenCode
lifecycle calls refuse before work, and await boundaries reject retired startup
or readiness results. Freshly spawned instances from retired startup are closed;
existing owned-process shutdown remains available. Health accounting and cached
results reset on selection revision changes. The startup wrapper does not start
the OpenCode watcher after its selection retires. An issued detection pass can
finish within its existing timeout, so this is not immediate network cancellation.
Protected runner enforcement and complete capability coverage,
unmigrated owned routes/UI remain activation
prerequisites. No CAgent host support is granted by this change.

`getSelectionSignal()` exposes the current host lifetime to owned OpenCode event consumers. Selection and clear abort the previous signal. The shared global hub stops its reader and clears replay; the push watcher detaches its subscriptions. Both reject retired readiness results and skip startup for CAgent. An unused hub also clears old replay when restarted under a different selection revision. This port grants no adapter authority and adds no HTTP selector.

## Protected adaptation packet runner

`createAgentPacketRunner` in `packet-runner.js` accepts protected host definitions, a frozen kit manifest and independent checkpoint read/write ports. Each packet has one canonical operation, its dedicated candidate directory, exact allowed text files, dependency operations and fixed named check functions. Definitions and checkpoints are host inputs; the runner never reads test commands, executable reports or approval requests from a candidate manifest. The offline kit must supply this composition before it can claim CA-02 delivery.

Before checks, the runner verifies the protected tree, captures bounded UTF-8 candidate files and verifies the complete candidate tree against that capture. Extra entries, unsafe paths, links, hard-linked candidate files, overlapping workspaces, malformed UTF-8 and excessive files/bytes are refused. Candidate hashes identify the captured content; they grant no trust. Checks receive frozen source strings and return strict booleans. The runner does not import or execute candidate code itself. A trusted fixture check that needs native candidate execution must supply its own documented execution boundary.

The runner verifies protected files, current candidate content and all direct/transitive dependencies again after checks. It persists only kit/operation/content identity, named boolean check results, checkpoint state and failure count. Reports contain fixed reasons and hashes, never source text, raw exceptions or paths. `fixtures-passed` proves this packet's checks only; it does not establish live support, host implementation or production activation.

A false fixture result consumes one implementation attempt. The initial attempt plus two corrections are permitted; the third failure requires a maintainer and stops further checks. Setup, boundary and checkpoint-port failures return a blocked result without consuming an implementation attempt. A fresh runner reads protected progress and revalidates dependency content; changing an accepted ancestor blocks its descendants. Each run still checks its own candidate, even if an earlier record says passed. Independent packets remain runnable.

One runner serializes its calls. The native workspace composition below adds persistence and exclusion across instances. Neither module configures filesystem ACLs, creates the offline bundle or writes activation approvals. CA-02 must prove those boundaries and its executable commands. Native file and fixture tests establish the implemented checks, not OS permission isolation or real CAgent compatibility.

### Native packet workspace

`createAgentPacketWorkspace` in `packet-workspace.js` composes the runner with an existing maintainer-owned progress directory outside protected-kit and candidate directories. It validates canonical native paths, regular single-link checkpoint files, bounded UTF-8 records and kit/operation identity. Missing checkpoints start an operation; corrupt or inaccessible checkpoints block it. Records are isolated by frozen kit digest, with no conversion of old kits.

Checkpoint writes use an exclusive owner-readable/writable temporary file, file sync and a same-directory rename. A failed replacement preserves the earlier record and cleans only this write's temporary file. This provides atomic visibility, not a power-loss durability guarantee. Maintainers must keep progress and protected definitions inaccessible to candidate writers through OS permissions; runtime path checks do not establish that permission boundary.

An IPC listener keyed by the progress directory's native device/inode identity excludes competing workspace processes for the entire run. Windows uses a named pipe; Linux uses an abstract Unix socket. These process-owned handles release after normal or abrupt process exit, following [Node IPC semantics](https://nodejs.org/api/net.html#ipc-support). Other operating systems return a storage refusal until an independently validated execution boundary exists. This restriction applies to the maintainer adaptation runner, not to app runtime support. The listener accepts no commands and closes incoming connections. No browser route exposes it.

Native Windows tests verify contention, forced owner exit, fresh-process recovery and the persisted three-failure ceiling. They do not prove Linux operation, desktop console visibility, ACL isolation or CAgent compatibility. Fixture success remains separate from maintainer activation and real environment acceptance.

## Goal reader migration

The OpenCode adapter exposes ordered `textParts`, `agent` and `variant` in its message view. The goal reader consumes these fields and existing explicit model/time/accounting fields instead of inspecting `raw`. `textParts` preserves text boundaries and excludes reasoning/tool content from the audit transcript. OC2 user/synthetic text is a single entry; absent text yields an empty array. Legacy `mode` supplies the agent only when `agent` is absent. The legacy variant and current model variant are projected at the adapter boundary.

This change applies to Web and the shared in-process Electron backend. Hosted mobile and Capacitor keep the same server-owned goal loop. VS Code does not gain a goal runtime or CAgent support. Goal sends, metadata, status, activity and event subscriptions still depend on OpenCode contracts; migrate and gate them before enabling CAgent goals. The neutral CAgent dispatcher is not connected to this reader yet. Existing SDK-shaped view types and raw records remain for other OpenCode callers. No acceptance or host-support row is enabled by this preparation.

Kernel HTTP regressions verify both protocol projections, and goal tests without a raw payload check multipart audit text, model/agent/variant continuation and stale identity refusal. These are fixture tests, not live CAgent acceptance.

Focused validation uses the package Vitest runner on `server/lib/agent/{approvals,artifacts,authority,attempts,dispatcher,schemas,content,routes}.test.js` and `contracts.test.ts`. Approval tests use native files and links, replace/delete records across reader restarts and revoke approval during dispatch. Content tests check typed parts, sparse metadata, permission semantics and nested import rejection. Authority tests compose synthetic registrations with independent approvals, including mismatches, revocation and dispatch. HTTP tests use real Express requests with a test authentication gate and synthetic accepted bindings. They cover body parsing, refusal codes, identity/availability snapshots, malformed requests/results, durable mutation/lookup and proxy isolation. They do not start the full production server or establish real CAgent compatibility. VS Code's `src/bridge-proxy-runtime.test.js` checks refusal before local or upstream forwarding. Directly compile `contracts.test.ts` with the installed TypeScript compiler as well. Its compile-only calls check operation-specific results, complete operation-key coverage, typed authority ports and rejection of missing workspace/request identity and unknown operations. The web workspace's normal type-check includes UI/src, not server declaration files.
